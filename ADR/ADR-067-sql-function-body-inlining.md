# ADR-067: SQL function body inlining

## Status
Accepted

## Context
A call of a STABLE function outside the allowlisted SELECT-list builtins forwards the read (ADR-065), whatever the function does. Supabase's `auth.uid()`, `auth.role()` and `auth.jwt()` are STABLE `LANGUAGE sql` functions over `current_setting('request.jwt.claims', true)`, and application helpers such as `current_tenant()` have the same shape, so every policy and every client predicate written against them forwarded (PGC-579). Three things stood in the way, and they fix where the change has to sit. The verdict judges a call by its `pg_proc` row and never sees the body. The session-term fold (ADR-066) keys a read on the fragments found at verdict time, so a `current_setting` inside a body is invisible to it even if something later replaced the call. And once a body replaces its call the function is gone from the tree, so nothing records the dependency the eviction on a function signal (ADR-065) and the hit's `EXECUTE` check (ADR-061) work from.

PostgreSQL inlines such functions itself at plan time (`inline_function`): a `LANGUAGE sql` function that is not volatile, not `SECURITY DEFINER`, without `SET` clauses, not set-returning, whose body is one SELECT, with the arguments substituted for its parameters and the result coerced to the declared return type.

## Decision
- **The catalog carries the body.** Beside each function's row the catalog loads what inlining needs: the body text (`prosrc`, only when there is no `BEGIN ATOMIC` body and the return type is a base, domain, enum or range type), `proisstrict`, whether `proconfig` is set, the parameter names and types and the return type as `format_type` spells them. Each eligible body is parsed once per catalog load into the form the inliner emits, and a catalog change (the function signal) reparses them and the loaded policies, as it already dropped the proxy's memoised verdicts.
- **Eligibility is PostgreSQL's rule, fail-closed where the proxy lacks what the planner has.** A sql function that is STABLE or IMMUTABLE, not `SECURITY DEFINER`, without `SET` clauses, not set-returning, with no variadic or defaulted parameter and no polymorphic type, whose body is one SELECT returning one column. A STRICT function with arguments is left out, since the planner's NULL test needs the argument values; a `BEGIN ATOMIC` body, since its stored form is already analysed; a body naming a parameter by name when it has a FROM, since a column of that name wins at origin and the proxy cannot tell them apart. A body with any other LIMIT than a literal 1 is left out too. Two rules are the call's rather than the body's: a body with a FROM, at its top or in a subquery, is not inlined for a call whose argument holds a column reference, since the body's tables would capture the name (`owner_of(id)` over `docs.id` would compare `docs.id` to itself and answer wrong silently), and a parameter the body uses more than once copies its argument per use, which is not done for an argument holding a subquery, as PostgreSQL does not. Such a call stays, the calls inside its arguments are inlined in its place, and anything else keeps the refusal it had, which names the function.
- **The inliner runs before the verdict, on both sides.** The proxy inlines the client query's calls before the cacheability check and the fragment scan, so the verdict and the fragments are those of what the body computes: `owner = auth.uid()` folds to the claim and is keyed on it like the claim written out. The writer inlines a policy's calls when it parses the policy, after qualifying them on its connection's path (ADR-065), for the same reason. A FROM-less body is the expression itself; any other body is a scalar subquery with `LIMIT 1` added when the body has none, which is what a call returns. Each argument is substituted for its parameter under a cast to the declared parameter type, each use its own copy, and the result is cast to the declared return type unless the body already casts to it, so the fold sees one cast over the Supabase helpers. Inlining repeats while a pass exposes further calls, up to eight passes; a body still holding one after the last is recursion and refuses the query.
- **Which function a call names.** A qualified call inlines the one function of that schema, name and arity. A bare call inlines the one function of the name and arity in the whole catalog: with a builtin or a second user overload of the name the call is nobody's alone and stays as it is. The proxy does not know the session's `search_path`, so the writer checks at registration that the path resolves each inlined call to exactly the function inlined, and otherwise refuses the read (`function_forwards{reason="inlined_elsewhere"}`), which forwards it to origin's own answer, including its error when the path does not reach the function at all.
- **The inlined functions travel with the query.** The cacheable query records each inlined call with its oid and a hash of the `pg_proc` row the body came from; the writer adds the oids to the entry's function oids, so a redefinition or drop on origin evicts the entry as it would a call the tree still showed, and adds the names to the read's privilege needs, so a hit still requires `EXECUTE` on them. A registration whose row has changed since the verdict (a redefinition that kept the oid, racing the function signal) is refused like a call resolved elsewhere, since the entry would hold a superseded body and no later signal would evict it. A policy's inlined calls join the read's when the policy applies.

## Rationale
- **Inlining at the verdict rather than at registration** is what makes the key the claim: the fold only knows fragments the verdict recorded, and the verdict is interned per statement text and shared by every session. Inlining at the writer would have cached `auth.uid()` reads per raw token, the cost ADR-066 exists to remove, and would have had to re-derive fragments on the bound tree, which ADR-066 ruled out.
- **The body replaces the call rather than being mirrored onto the cache database.** A mirrored body that reads a table would see the cache's partial tables and answer wrong silently (ADR-065); the inlined body reads the tables as part of the query, so they join the entry's maintenance and population like any other reference.
- **Unique in the catalog, checked on the path** inlines the common application helper written bare (`current_tenant()`) while a wrong guess is impossible: the writer's check is the same resolution the entry's other calls get, and the refusal is exact.
- **`LIMIT 1` on a body with a FROM** keeps a call's first-row semantics where a scalar subquery would error on a second row. A correlated such body would not decorrelate (ADR-015 refuses a non-aggregate scalar subquery with a LIMIT), but a FROM body never takes a column argument, so once the session terms fold the subquery is uncorrelated.
- **Casting every argument** mirrors the coercion the planner inserts and is needed for correctness (`$1 / 3` with a numeric parameter and an integer argument); its cost is that a column argument under a cast is opaque to the predicate model, which is a precision loss, not a wrong row.

## Consequences

### Positive
- `WHERE owner = auth.uid()`, `auth.role()` and `auth.jwt() ->> 'sub'` in a client query, and a policy `USING (owner = auth.uid())`, are cached and keyed on the claim: two tokens of one user share one entry, as with the claim written out.
- An IMMUTABLE sql helper with arguments (`double_it(n)`) is cached without the cache database holding it; a STABLE helper reading a table under a session term is cached and maintained by CDC on that table.
- A redefinition of an inlined function evicts its entries; a role without `EXECUTE` on it still forwards.

### Negative
- A body is inlined as text parsed under pgcache's converter, so a body using a construct the converter does not model keeps the call, and the refusal of a stable function.
- A body with a FROM called with a column argument (`owner_of(id)`) is not inlined and forwards; so does a FROM-less body whose column argument the cast makes opaque where a predicate was needed for a constraint.
- A FROM body inlined where the call is the whole predicate (`WHERE is_visible()`), or a boolean FROM-less body in a WHERE, is emitted in its SELECT-list spelling (a scalar subquery, `Operator` rather than `Binary` nodes), which the predicate model treats as opaque: correct, but the read gets no constraint from it (PGC-597).
- A bare helper of a name two schemas define is never inlined; qualify the call or the name.
- A policy's function body that reads a table by a bare name makes the policy uninlinable: the body's tables resolve on the reading session's path at origin, which the writer's policy parse does not have; qualify the table in the body.
- Every inlined call costs the writer one path resolution per registration, and the catalog load parses each eligible body once.

## Implementation Notes
- Inliner: `query/transform/function_inline.rs` (`function_body_parse`, `FunctionBody`, `query_tree_functions_inline`, `InlinedCall`); the body columns and `FunctionSource` on `FunctionRow`, the parsed bodies on `FunctionCatalog`, and `FunctionFacts::inline_body` in `catalog/function.rs`.
- Proxy stage: `CacheableQuery::classify`/`try_new` in `cache/query.rs` inline before `cacheable` and record `inlined_calls`; `proxy/query.rs` (`analyze`) classifies and keeps the tree as written for the volatile scan.
- Writer stage: the path check and the oids in `writer/registration/resolve.rs` (`functions_resolve`), the privilege names through `ResolvedQuery::privilege_functions_extend`; policies inlined in `writer/rls.rs` (`rls_qual_parse`), their calls carried by `RlsInlined`.
- `query_tree_parse` returns a parse error instead of panicking, since bodies are user text.
- pgcache-fit's snapshot carries no bodies (`fit/data/functions_regenerate.sh` cuts the columns), so a builtin is never inlined there, as on the proxy.
- Tests: `tests/function_inline_test.rs`; the policy case in `tests/rls_test.rs`; the inliner's unit tests in `function_inline.rs`.
