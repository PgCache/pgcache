# ADR-056: Per-Connection Session Settings

## Status
Accepted

## Context

A cached result is only valid for a client whose session settings match the ones it was computed under: `search_path` decides which table a bare name is, `TimeZone` and `DateStyle` decide what a literal means and how a timestamp is rendered, `role` decides which rows a policy exposes. Before this decision the proxy tracked two settings, each with its own machinery: `search_path` through a raw-tree classifier, a piggybacked `SET …; SHOW search_path` rewrite of the client's own query and an unconditional re-probe at every transaction end before PostgreSQL 18 (ADR-006), and `default_transaction_isolation` through the statement analyzer's effects and a block-scoped state (ADR-054). Nothing else was tracked, so PGC-287's other classes had nowhere to land, and the two trackers duplicated mutation detection, block handling and probing.

Alternatives were a third tracker beside the two (rejected: the ticket asks for one mechanism), and deriving the search_path view lazily on each read (rejected: the hot path clones a precomputed `Arc` and should keep doing so).

## Decision

- **One state per connection.** `SessionSettings` holds every tracked setting (a fixed `Guc` enum: name resolution, literal semantics, text rendering, identity, and the isolation default) with a session value and an optional block value, each known or unknown. The resolved search_path and the isolation default are views derived from it when it changes; the block-level isolation logic of ADR-054 stays and reads the session default from the view.
- **One classifier.** The statement analyzer's `StatementEffects` gains a settings effect: which settings a statement may change, whether the change is block-scoped (`SET LOCAL`, `set_config(…, true)`), whether it may be anything (`RESET ALL`, `DISCARD ALL`, a `set_config` whose name is not a literal), and whether a `ROLLBACK TO SAVEPOINT` may have reverted block values. It is memoised with the verdict and applied by the single forward-effects method. The search_path classifier, both inspect hooks and the piggyback intercept are gone.
- **One probe.** `ProbeKind::SessionSettings` samples every tracked setting in one `current_setting(…)` row, as an ordered egress slot (ADR-055). It is injected at any origin ReadyForQuery when something is unknown at the read's scope and none is pending, inside blocks included: the probe's own status byte scopes the sample as session or block state, a failed-block sample is discarded, and the isolation default is taken only from an idle sample since PostgreSQL reads it at `BEGIN`.
- **Reported settings are origin's.** A setting origin has reported by `ParameterStatus` (always for `client_encoding`, `DateStyle`, `TimeZone` and friends; `search_path` from PostgreSQL 18) is updated from each report and never marked unknown by a statement.
- **Scope follows the statement, not the block end.** A session-scoped `SET` marks the session value unknown at forward time, inside a block or not; a block-scoped one marks only the block value. Block exit drops block values. A block that touched nothing needs no probe when it ends.
- **A probe fills only what was unknown before it.** Mutations are numbered; the probe carries the number at its injection and its sample never fills a value a later statement marked, since the sample predates that statement on origin, and never overwrites a known value.
- **Unknown forwards.** A cacheable read is keyed only when every tracked setting is known at its scope and the search_path does not shadow builtins (ADR-006). Values are tracked here; what each class of setting does to keying and serving is decided by the later PGC-287 slices.
- **Literal semantics are the reference's (class 2, part A).** Origin's defaults for `TimeZone`, `DateStyle` and `IntervalStyle` are read once per cache generation and pinned on every session pgcache owns (writer, population, MV build, CDC write and eval, and the replication session, where `DateStyle` output is forced to ISO), so population, PgEval and pgoutput text agree on what a literal means. The local evaluator and the eval index compare a literal against row text by the column's type rather than as bytes (ADR-027, ADR-037 amended; PGC-478). Four settings that change how origin parses a statement forward the session while set: `standard_conforming_strings` off, `transform_null_equals` on, `array_nulls` off, `gin_fuzzy_search_limit` non-zero. Population, PgEval and pgoutput text therefore agree with each other; what they agree with the *client* is part C.
- **Literals are canonicalised at registration (class 2, part C).** The four settings that fix what a date-time literal means (`TimeZone`, the order half of `DateStyle`, `IntervalStyle`, `timezone_abbreviations`) travel with the read as `LiteralSettings`, and join the session key of any query with a string literal. On resolution the writer rewrites each literal whose type it can see — beside a column, in a column's IN/ANY list or BETWEEN bounds, or under a cast — to a settings-independent spelling under the registering session's values: ISO dates and date-times, instants with an explicit offset (a zone-less `timestamptz` literal through the session zone, from the bundled zone database), ambiguous numeric dates by the session's order. The cache identity is the hash of this resolved form, so two sessions whose literals mean the same rows share an entry and two whose literals differ never do; the typed comparator sees only canonical literals and keeps evaluation local. A literal the pass does not handle (a month name, a special word, an interval, `date` ↔ `timestamptz` conversion, or a digit-bearing string in a position whose type it cannot see, such as a function argument) is left as written and interpreted under the reference at population; the entry is marked reference-only and served only to a session whose literal settings equal the reference's.
- **Rendering settings travel with the read (class 3).** The eleven settings that decide how a text result is rendered (`TimeZone`, `DateStyle`, `IntervalStyle`, `extra_float_digits`, `bytea_output`, `client_encoding`, `lc_monetary`, `lc_numeric`, `lc_time`, `xmlbinary`, `xmloption`) are snapshotted at dispatch as an `OutputSettings` profile. A serve applies them on its pooled cache-DB connection with one prepared `set_config(…)` statement pipelined ahead of the generation stamp and the SELECT, consumed by the response state machine like the stamp; each connection remembers the profile it last applied and sends nothing when it is unchanged. The profile hash keys memo entries and coalesce groups, so one client's rendering is never handed to another. It covers every value whatever the result format: binary results carry no protocol-level rendering, but a query can compute zone- or locale-dependent text itself, so sharing binary results across settings waits for the class 2 slice.

## Rationale

- **Correctness needs the whole list.** Each class of setting has its own handling rule, but every one of them needs the same tracking: a value per scope, invalidation by statement, recovery by report or probe.
- **The analyzer already sees every statement.** Classifying settings where write class and isolation are classified gives one memoised pass and one apply point, instead of a second raw-tree walk per statement.
- **Slot probes remove the reason for the piggyback.** With no quiescence condition and no starvation (ADR-055), a lazy probe after a `SET` costs the same single round trip as rewriting the client's query, under both protocols.
- **Transaction-end re-discovery was a proxy for scope.** Marking at forward time, in the scope the statement names, makes the block end a no-op for untouched settings (PGC-216).

## Consequences

### Positive
- `SET LOCAL` and `set_config(…, true)` are tracked for in-block serving (ADR-054).
- `$user` expands against the current role and session authorization rather than the startup user.
- One probe per fresh connection instead of two before PostgreSQL 18; none after a transaction that changed nothing.
- No query rewriting on the client's connection; the only remaining intercept strips a lazy `Parse`.

### Negative
- Every fresh connection waits one probe round trip before its first cacheable read is keyed, on PostgreSQL 18 too (its reported settings do not cover the unreported ones).
- `txn.isolation_probes` is replaced by `conn.settings_probes`.
- A client's `lc_monetary`, `lc_numeric` or `lc_time` must name a locale the cache cluster's host has; otherwise applying them fails on the cache DB and the hit forwards (the serve-pool error path), every time.
- A client on different rendering settings from the ones a memo was captured under misses that memo and takes the serve pool; a binary-format client does too, since a query can still compute settings-dependent text.
- A session on literal settings other than origin's defaults forwards every hit on a reference-only entry, and every digit-bearing string literal in a blind position (`lpad(x, 5, '0')`) makes its entry reference-only; the pass is conservative where it cannot see a type.
- The writer resolves a query twice on its first appearance under a (path, settings) pair: once to answer `Resolve`, once to register. Fingerprints are not persistent, so changing what they hash costs nothing across restarts.
- The tracked list is fixed; custom settings read by policies (`app.*`, `request.jwt.claims`) are the class 4 slice's extension of it.
- A `SET` executed inside a function body, and a `postgresql.conf` reload under a live session, remain unobservable (as in ADR-054).

## Implementation Notes
`proxy/session_settings.rs` is the pure state and its derived views; `proxy/connection/probe.rs` injects and applies the probe; `query/guc.rs` is the tracked list and the probe column order; the settings effect lives in `query/write.rs` and is produced in `query/ast/convert_raw/write.rs` and `proxy/query.rs`. `cache/output_settings.rs` is the rendering profile and its statement; `pg/cache_connection.rs` applies it and remembers it per connection. `query/literal_settings.rs` is the literal profile; `query/transform/literal_canon.rs` the canonicalisation pass, run by `cache/writer/registration/resolve.rs` on both the resolve and register paths; `query/resolved::resolved_query_fingerprint` the identity; `cache/reference_settings.rs` holds the reference the dispatch gate compares against. Supersedes ADR-006's acquisition strategy and amends ADR-054's isolation discovery; ADR-006's keying and resolution sections stand.
